# PPT Page Pattern Library

Use this reference when generating page-level image prompts. These are reusable visual patterns, not project-specific templates. Select one pattern by page role, then adapt the objects, labels, screenshots, and evidence to the user's topic.

## Pattern Selection

- Cover or solution overview -> Product Hero Cover.
- Capability, feature, or module overview -> Screenshot Feature Cockpit.
- Policy, standards, report, or decision background -> Evidence Roadmap.
- Governance, audit, safety, operations, or proof page -> Audit Evidence Cockpit.
- Pain point, current state, or gap diagnosis -> Fragmentation Diagnosis.
- Process, workflow, or teaching project chain -> Output Pipeline.
- Architecture, platform, or deployment page -> Layered System Architecture.
- Value summary or closing page -> Value Closure Map.

Do not reuse one successful layout for every slide. Use the pattern only as a starting structure.

## Product Hero Cover

Use for cover pages, solution introductions, product-led opening pages, and first-view proposal pages.

- Primary visual: one large real product screenshot, UI cockpit, device mockup, or solution scene.
- Best structure: left title/support group, right large perspective hero visual, subtle topic context in the background.
- Information budget: one hero visual, one subtitle/value statement, 3-4 compact tags or proof points.
- Alignment: title/support group shares one left edge; tags align as one group; hero visual stays within right/bottom safe margins.
- Title safety: keep the upper-left title area clean. If the hero visual overlaps the title span horizontally, its top edge should usually start below the title breathing area. If the hero enters the header, it must stay far right and be soft/non-critical.
- Avoid: split-screen flat layout, generic stock photo, hero visual touching the page edge, tags scattered around the page, screenshot visually attached to title text.

Prompt structure cues:

- "Visual role: product hero / immersive solution cockpit cover."
- "Use the provided real product screenshot as the required hero visual; preserve it as recognizable product UI, not fake UI."
- "Left support group starts below the title safety area; right hero panel occupies about 55%-65% of usable body area."

## Screenshot Feature Cockpit

Use for product capabilities, feature overviews, multi-modal ability maps, platform modules, and "what the product can do" pages.

- Primary visual: one large real screenshot plus 2-4 smaller screenshot panels arranged as a spatial cockpit or screenshot wall.
- Best structure: supporting capability modules on the left or top, screenshot cockpit on the right/middle, optional aligned value strip.
- Information budget: one screenshot cockpit, 3-4 capability modules, at most one closure strip.
- Alignment: repeated capability modules share width, x/y reference, internal padding, icon starts, and label starts. Screenshot panels share a clear perspective grid or right boundary.
- Title safety: strong screenshot edges must not enter the local title collision zone or attach visually to the title. Use a clear gap under the title before large panels begin.
- Avoid: equal-weight flat card grid, tiny screenshots that lose proof value, screenshots used as generic decoration, floating tags between modules, conclusion strip with arbitrary indentation.

Prompt structure cues:

- "Visual role: capability page / product feature cockpit."
- "Required real screenshots are subject-content layers; preserve them as recognizable product screenshots."
- "One large hero screenshot, supported by 3-4 smaller screenshot panels layered in perspective."
- "Capability tags belong inside their parent modules; do not fill gaps with floating labels."

## Evidence Roadmap

Use for policy background, standards evolution, market milestones, report evidence, certification paths, and official decision timelines.

- Primary visual: 3-5 evidence objects, usually document cards, report sheets, plaques, or source panels.
- Best structure: horizontal or slightly arced roadmap line with evidence cards attached to nodes; optional bottom takeaway aligned to the same bounds.
- Information budget: one roadmap, 3-5 evidence objects, 3-5 short support labels, optional aligned takeaway.
- Alignment: evidence cards share baseline or centerline; date/node positions are consistent; closure strip aligns exactly to roadmap/evidence bounds if used.
- Title safety: first card or roadmap line must not crowd the title. Upper-right can carry soft institutional context, but not dense foreground content.
- Avoid: document cards with inconsistent sizes, badges filling gaps, bottom takeaway floating wider/narrower than the roadmap, overly dense official text.

Prompt structure cues:

- "Visual role: policy evidence page / strategic roadmap."
- "Official facts become evidence document cards; the roadmap is the primary visual."
- "If a bottom takeaway strip appears, align its left and right edges exactly to the roadmap/evidence group bounds."

## Audit Evidence Cockpit

Use for governance, content safety, review, audit, traceability, asset sedimentation, monitoring, or compliance pages.

- Primary visual: real dashboard/screenshot evidence, usually one large list/control panel plus one smaller detail/proof panel.
- Best structure: 2-3 governance modules on one side, screenshot evidence cockpit on the other, restrained flow cue between them.
- Information budget: one screenshot cockpit, 2-3 supporting governance modules, one light flow cue. Avoid a separate bottom closure unless truly needed.
- Alignment: support modules share one grid; screenshot panels share one cockpit grid; flow lines belong to the relationship and stay subordinate.
- Title safety: dashboard edges, cards, dense UI text, glow, and connectors must stay outside the title collision zone and local breathing area. A screenshot slightly below the title but visually attached still fails.
- Avoid: generic security shield replacing the real screenshot, too many small badges, screenshot panels touching the top/right edge, flow lines crossing the title area.

Prompt structure cues:

- "Visual role: governance evidence page / platform audit cockpit."
- "Real screenshots are required evidence, not fake UI."
- "Main screenshot starts below the title clearance zone with a clear visible gap; foreground proof panel aligns to the same grid."

## Fragmentation Diagnosis

Use for pain points, current-state analysis, before-state pages, disconnected workflows, risk maps, and gap diagnosis.

- Primary visual: a fragmented center system, broken workflow, disconnected tools, risk board, or bottleneck map.
- Best structure: central current-state visual with 4-6 aligned issue modules around it, or two-column contrast if before/after is explicit.
- Information budget: one diagnosis visual, 4-6 issue modules, optional highlighted constraint or consequence.
- Alignment: issue modules should follow a clear ring, grid, or column system. Do not place modules wherever space remains.
- Title safety: diagnosis visuals can be expressive, but dense issue cards and connectors must not crowd the title.
- Avoid: every issue as an equal heavy card, random connector webs, dense warning colors, modules pushed to page edges.

Prompt structure cues:

- "Visual role: pain-point diagnosis page."
- "Translate abstract issues into visible broken relationships, disconnected tools, or bottleneck objects."
- "Use a clear module grid/ring; no floating issue cards."

## Output Pipeline

Use for workflows, teaching projects, production chains, content generation steps, implementation paths, and training processes.

- Primary visual: path, pipeline, stage chain, before/after sequence, or production conveyor.
- Best structure: left-to-right or top-to-bottom flow with stage outputs as visual proof objects.
- Information budget: 4-6 stages, one primary path, one optional outcome/asset destination.
- Alignment: stage cards share baseline/centerline; output thumbnails belong to each stage; endpoint aligns to the path.
- Title safety: path should begin below the local title breathing area unless it is a soft background guide.
- Avoid: tangled arrows, too many sub-steps, equal emphasis on every minor output, endpoint floating away from the path.

Prompt structure cues:

- "Visual role: process page / output pipeline."
- "Each stage has an information-bearing object or output thumbnail."
- "Use one primary flow path; do not add secondary arrows unless they clarify the workflow."

## Layered System Architecture

Use for platforms, deployment, local infrastructure, system architecture, capability stacks, and solution blueprints.

- Primary visual: layered stack, base platform, hub-and-spoke structure, or connected architecture diagram.
- Best structure: stable base layer, middle platform/capability layer, upper application/user layer; optional side proof object.
- Information budget: 4-6 architecture layers or groups, one main system spine, limited annotations.
- Alignment: layers share width logic and centerline; related modules share vertical rhythm and connector rules.
- Title safety: architecture top layer must not crowd the title; use background structure lines sparingly.
- Avoid: too many tiny nodes, decorative circuit noise, inconsistent layer widths, unreadable micro labels.

Prompt structure cues:

- "Visual role: architecture page / platform blueprint."
- "Use a layered architecture with consistent width logic and clear base-to-application hierarchy."

## Value Closure Map

Use for summaries, benefits, closing pages, stakeholder value, conclusions, and procurement/decision takeaways.

- Primary visual: closed loop, value matrix, stakeholder map, equation-style platform value, or highlighted conclusion system.
- Best structure: central value claim or loop with 3-4 stakeholder/value modules around it.
- Information budget: one conclusion system, 3-4 value modules, one concise final statement.
- Alignment: surrounding modules share grid or radial logic; final statement aligns to central system or page bounds.
- Title safety: central conclusion may be large, but must start below the title safety area unless designed as title support.
- Avoid: generic icons with no relationship, decorative rings without meaning, too much explanatory text.

Prompt structure cues:

- "Visual role: value page / closing synthesis."
- "Translate value into a visible closed loop or stakeholder map, not a list of benefits."

## Common Failure Corrections

- If a page feels flat: introduce one primary visual at 40%-65% of usable body area and reduce equal-weight cards.
- If a page feels crowded: remove micro labels, extra icons, decorative connectors, or optional closure before reducing spacing.
- If alignment fails: name concrete bounds and reference objects in the prompt, including repeated module width, shared baseline, and closure alignment target.
- If the title feels crowded: move strong subjects out of the local title breathing area or turn nearby header content into low-contrast atmosphere.
- If real images are weakly used: assign each image a role, such as hero screenshot, evidence panel, local zoom, output proof, or background atmosphere.
- If the user provides real image addresses or folders: resolve the actual image files, verify they are readable, and make them available as direct image inputs or visible conversation references before generation.
- If real images are required but only local paths are written into the prompt: stop and fix the input method. Paths, filenames, and descriptions are addresses to resolve, not visual inputs, and must not be treated as proof that the real images were used.
