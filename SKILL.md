# PPT Image ZLX Workflow

## Route by task

- Existing board URL and request ID — verify once that the current chat is a project-bound Codex chat, then run `prepare --url <board> --request-id <id> --packet-only` with the installed skill runner at `<skill-root>\scripts\page-task.mjs` (resolve `<skill-root>` from this skill's `SKILL.md`, never from the project directory). Read its page input once. On a fresh design, read applicable planning rules together once; on `reuse:true` (QA-approved exact-fingerprint design), verify artifact hashes and the complete image-input set, then skip rule rereads and brief rewriting. Treat `inputReuse:true` as an unvalidated draft. Successful `ready` and image QA automatically record the exact generation input contract for future reuse; localized edits are never promoted as standalone designs. The command recipe is in `references/single-page-execution.md`; consult it when needed, and defer QA/recovery references to their actual stage. Verify prepare returned `sessionFile`, then use `ready --session-file`; every new image still needs full QA. Stop after registering one candidate for acceptance.
- New project, source normalization, outline, board creation, master/style definition or batch planning — read `references/workflow-authoring.md`, which preserves the complete authoring workflow and review gates. Then load only references required for that stage.
- Workflow maintenance or release — use the maintenance sections of `references/workflow-authoring.md`. Preserve existing changes. Verify and push only when the user requests release.

## Existing-page execution

The confirmed page request authorizes its internal design and prompt preparation. Preserve its board, request ID, fixed page ID, scope and source boundaries. Use the execution package for current content, global/page choices, assets, source freshness and rule requirements. Never reconstruct a project or add a prompt-approval pause for an existing reviewed request.

Keep pre-generation work to one preparation, one grouped input/rule read, actual image inspection and one page-specific brief. Reuse rules already read in this chat while their hashes remain current. The program copies confirmed decisions into the guide; keep the brief's layout, color roles and treatment mapping concise and put the full image instruction only in prompt. Build the brief as a JavaScript object and write it with Node.js `JSON.stringify`; do not hand-quote multiline JSON in PowerShell or shell. Let the existing commands validate brief/QA structure and record timings; do not hand-build JSON logs or add another validation step. Once design and actual inputs are verified, combine ready, official generation and native-file finalize in one orchestration following the handoff recipe. A current chat identity already verified in this session needs no per-page metadata query.

Read the input packet's applicable planning rules once before writing or revising the prompt. Existing pages use `single-page-design-contract.md`; the project-wide page-guide template belongs to new-deck authoring. The program saves confirmed decisions and source identity into the guide from one compact design brief. Read `qa-gates.md` when inspecting the actual generated image. First table designs, redesigns and visual-rule revisions require `table-visual-art-direction.md`. Read recovery/repair details after an actual exception. Keep full rules on disk and avoid reprinting already-read inputs, prompts, manifests or complete rule files in progress messages.

An exact-fingerprint recorded input may be reused as an unvalidated guide/prompt draft after artifact-byte checks. Its `inputReuse` flag does not certify visual quality or permit skipping applicable rule review. Only `reuse:true` with a verified complete image-input contract can skip rule rereads and brief rewriting. Every newly generated image still needs actual-image QA. Rebuild changed inputs and invalidated designs. `--rebuild-inputs` explicitly disables draft reuse. Follow the guide's concrete visual design, including semantic imagery and module treatment.

## Content and visual invariants

- Follow explicit confirmed `content_handling`. Strict mode retains required wording, facts, units, qualifications and order, subject to exact user-selected span treatments. Interpret mode allows source-grounded synthesis while preserving essential facts, relationships and locked wording. Follow `information-priority.md` for emphasize, condense-illustrate, soften, replace and text-only treatments. Design text-bearing modules together with semantic imagery and contextual details.
- Preserve source/module reading order, genuine relationships, confirmed titles, placeholders and user-locked wording. Respect group priorities without inventing narrative reorder, facts, evidence or official logos. Preserve the board's palette roles, expressive level, title policy and real-image roles. Keep mandatory text comfortably readable.
- Screenshot mode uses actual screenshots as its sole content source. Follow `screenshot-extraction.md`; preserve words, numbers, units, qualifications and merged-table relationships. Rebuild from screenshot meaning with current board visual choices. Inactive Markdown and hidden legacy production annotations supply no slide content. Confirmed real assets remain required.
- Read actual required images. A path printed in a prompt does not supply an image. Use actual image input, or display and explicitly reference the image when the official tool supports that method. Report unreadable facts and tool limitations accurately.

## Generation and QA

Run single-page generation in a Codex local project chat. This workflow requires local project access for `page-task` and a native PNG path that can be finalized into the board. Changing the mode on an existing chat does not change that chat's actual type or bind a project directory; verify the current chat identity and project access once per chat. If either is missing, preserve the request and report the limitation before generation. This is a file-handoff requirement, not a visual-quality requirement. Follow `references/native-image-execution.md` for normal image inputs and native output. Read `references/page-input-packet.md` only for supplemental references or when its transport plan reports a capability review. Read `references/image-result-handoff.md` only after an actual delivery error or when a localized repair is needed.

Use the official `image_gen.imagegen` with the exact checked prompt and required actual images. Display with `generatedImage(result)` and immediately finalize through the existing local command route using only the official native PNG path and actual timestamps. Keep image bytes out of subsequent tool arguments and messages. Preserve the existing body/final directories and title policy.

Use `ready` to record and check inputs. Read inputs and applicable rules once, and resume saved stages from the same request's progress and image receipt. Saving or registration failures reuse the existing image; retry after a concrete correction or known transient failure, once per unresolved failure. Tool permissions remain client-controlled.

Inspect content, layout and visual completion against the actual image. Keep table-specific evidence and high-impact repair requirements. If no-title body/final files have identical verified hashes, one inspection of those same image bytes may support both stages. Title overlay requires final-image collision checks. Return a file-backed passing candidate and wait for acceptance. Never automatically adopt or process another page. Treat text-only findings (wording, labels/fields, values, units, punctuation, font sizing and text appearance) as concise `textFeedback` for the user; do not regenerate solely for them. Full-width or half-width comma separators are acceptable when meaning is unchanged. Continue to block on non-text compliance, information-layout or visual failures. Show `textFeedback` in the existing result footer without adding a step.

## Cost and recovery

Let programs handle deterministic work: parse and serialize files, validate schemas and hashes, check freshness, save outputs, record timing and verify lineage. Let the model handle source meaning, design choices, prompt intent and visual QA against the actual image. Never automate away semantic design judgment or visual checks. Return concise status, artifact paths and current differences after the input package has been read. Resume from `task-progress.json` and the immutable execution record instead of reconstructing chat history. Keep image generation and saving failures distinct. Request authorized project access when needed and allowed; respect explicit approval denials. Keep the same request and outputs during recovery.
