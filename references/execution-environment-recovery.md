# Single-page exception recovery

Load this file only after an observed failure, ownership conflict or interrupted conversation. The normal execution path is defined solely in `single-page-execution.md`. For a new design, prepare returns sessionFile and page-input.json. Write one design brief, then use ready with --session-file and --brief-file. The older explicit manifest/worker and separate guide/prompt forms below remain compatibility and recovery details.

For current tasks use prepare --packet-only and read its page-input.json once, as described in `page-input-packet.md`. Declare every required base slide and crop with --references-file before relying on a repair prompt. ready/check write tool-input.json with exact prompt, complete image inputs and a transport plan. The --packet-only form avoids repeating the full input and prompt in model-facing command output. Existing command forms remain supported.

Preparation uses the exact request API input directly. Browser navigation is unnecessary when that package is available. The package already includes saved global/page decisions and active assets. Prepare once, group the applicable rule and image reads, then write one guide/prompt and call ready. Worker/asset/source validation remains in the program. An unchanged verified standalone design needs no redesign; an incomplete edit-reference draft must be rebuilt once with its complete inputs, without repeated historical searches.

For timing, page-task results expose localChecksMs, ownershipMs and executionMs. These measure local operations and exclude model planning, client approval wait before invocation and image service time. Capture callStartedAt immediately before the actual image tool and toolReturnedAt immediately after it. The receive helper records toolWaitMs, handoffDelayMs and saveMs separately. Do not label the interval after generation check as pure pre-generation checking, and do not attribute unmeasured delays to copying or image service latency.

Before declaring a fresh generation's recorded inputs reusable, confirm that every image referenced by its prompt exists in the execution package and has been read. Mark record/ready with --source-only-inputs only when those packaged assets are the complete image reference set. Base-slide edits and crop-dependent repairs use --localized-repair instead. The current entry excludes cross-request caches lacking this explicit standalone-input contract. Matching text hashes alone cannot establish complete image inputs. Same-run recovery retains its original artifacts for checking; do not silently drop missing reference images.

For image input, result receipt and localized repair follow `image-result-handoff.md`. In particular, prefer an already-authorized local command route, use receive/finalize for both embedded PNG and native file returns, and reuse the successful image as the base for an observed local defect. This retains all current content, image and visual QA requirements.

When a chat reaches its context limit, preserve the exact request and artifacts. In a continuing chat, inspect returns a bounded execution summary with guide/prompt paths and the next stage. Read that summary and the saved current input instead of previous chat history or the complete manifest. For an unchanged recorded design, verify its immutable artifacts and reuse the exact prompt; do not reload planning references or redesign it solely because the chat ended. Load visual QA rules when an actual image is available. If the last record only has generationCheckAt, locate any preserved official result/output_hint before generating again; the check timestamp does not prove whether the official tool returned an image. Do not infer missing output from a missing preview.

Keep model-facing context bounded by reading the current page input once, applicable rule files once per required design/QA stage and the exact saved prompt only for its actual tool call. Do not echo complete guides, prompts or rule text after saving. Keep image data and encoded bytes out of text outputs, command arguments and logs. Keep full artifacts on disk. For a failed operation, return the original error and one specific recovery step; avoid repeated exploratory tool changes or rebuilding verified artifacts. This limits duplicated context without shortening required slide text, weakening table/visual rules or skipping actual-image QA.

For a fresh queued exact-ID task, prepare is the first execution operation. It already performs the read-only identity/source checks. Do not separately run inspect, scan other requests, enumerate Windows processes or search historical executions before prepare. Those recovery operations apply only to a real running-owner conflict, an invalid supplied request or an observed execution failure. If the exact ID is terminal, report that status and the current same-page request as information; never silently execute a different request. The board's copy action refreshes the page's current request before producing instructions.

Use an already-authorized local command tool for filesystem/script work when available. Keep the same route across successive steps. The module also exports runTask for an authorized in-process Node runtime when needed. Ordinary preparation needs no GUI Computer Use, app-window access, administrator privileges or global process discovery. Do not proactively request those permissions after local access has succeeded. Respect actual permission denials. Client-required tool approvals cannot be suppressed by this skill; request only the specific failed operation if policy permits. Retain a persistent authorized runtime for successive steps instead of initializing a different tool for each operation.

For a fresh design, group applicable rule-file reads and actual required image inspection into one preparation stage, then write the guide/prompt and run ready. Keep user progress to meaningful changes; avoid narrating every ID/status check. The design stage still must preserve source facts, module semantics, style, actual image assets and table structure, and every new image still requires actual visual QA.

For a new design, prepare once, read its input and applicable rules once, then save a compact page guide and a separate exact prompt file. Refer to the prompt file from the guide instead of duplicating the full prompt. Use `ready --manifest <file> --worker-id <id> --guide <guide> --prompt <prompt> --verified` to record, start and check in one command. Screenshot tasks also pass `--extracted-source <file>`. It returns the exact prompt and image inputs for the official tool. The official image call and actual visual QA remain model steps. A repeated ready with identical input files preserves its existing attempt. A saved finalized output returns `generationRequired:false` and directs continuation to QA/complete.

`inputReuse:true` means exact-fingerprint, byte-verified guide/prompt inputs are available. Read and verify those artifacts against the current task instead of rewriting them; retain their unvalidated status until actual-image QA. Use ready without guide/prompt arguments to continue these frozen inputs. `--rebuild-inputs` on prepare disables reuse for explicit redesign. On resuming in a chat that already read the inputs, `prepare --summary` omits the repeated input package. A new chat must still read the saved input and relevant assets. Each command writes a compact task-progress.json beside its manifest and returns elapsedMs. Use this summary for recovery; preserve existing original outputs.

For an exact board URL and request ID, use `scripts/page-task.mjs` from this skill directory for all execution commands. It routes screenshot and Markdown tasks automatically through the existing execution implementation. Follow `references/single-page-execution.md` for design, official image generation, QA and finalization. Read the input package's `requiredReads`. Screenshot tasks also follow `references/screenshot-extraction.md`; the single design brief carries extractedSource.

Run `node scripts/page-task.mjs prepare --url <board-url> --request-id <exact-id>`. It verifies the assigned page, reads source/assets and checks saved execution identity without synthetic write probes, then writes or resumes the actual immutable execution record. Actual write failures report their original code and stage. It returns `manifest` and `workerId`. Keep that worker ID for this chat and pass `--worker-id <workerId>` with every subsequent command and repeated prepare. An existing owner blocks a second chat. After confirming the original worker has stopped, another chat can use `prepare --confirm-stopped` with the same request ID to take over. Do not infer that a quiet heartbeat means the original worker stopped.

`inspect --url ... --request-id ...` performs read-only environment checks and reports `manifestExists` separately from its expected path. It does not establish project write capability. Preparation relies on actual execution-record writes; guide/prompt files are checked when recorded. `check --manifest ... --worker-id ... --include-prompt` verifies the output directories before returning the exact prompt and input images for the official tool. Check that `image_gen.imagegen` is available in the executing chat before start. The script cannot verify the chat's tool inventory or guarantee tool acceptance of an image input.

Permission errors return the original code, failing stage and `guidance`, and report the blocker to the assigned board when reachable. If the current session allows permission requests, request the access needed for that same already-authorized project operation and retry that exact command with the same worker ID. If policy explicitly denies approval, report that refusal and continue in a local project chat with the required access. Do not repeatedly request a forbidden approval or switch tools to circumvent a denied permission. A tool authorization prompt and filesystem write access are separate capabilities.

Choose an available, already-authorized local execution tool for the project before beginning. The module exports runTask for direct use in a supported local Node runtime as well as its CLI. Use the same execution implementation, exact prompt, image assets and QA in either case. An authorized tool's presence does not establish filesystem write access. Diagnose a real write failure in its actual runtime before changing tools or settings. On Windows, compare the workspace and project ACLs when the workspace is writable but existing project descendants are denied; enabled inheritance can still have stale inherited entries. Any access repair must stay within the explicitly authorized project and preserve file contents, visual rules and board decisions. A blocked initial prepare with no saved execution record releases only its own worker claim, allowing the same queued request to retry after access is restored. Existing execution records and active workers retain ownership protection.

If the client reports that an approval request is no longer active, check the request and existing artifacts before reissuing the same unfinished action with a fresh approval when permitted. An inactive approval alone does not establish policy denial, project corruption or image-generation failure. Do not create a replacement request or restart a successfully completed image operation. Client approval lifecycle errors can occur outside the script and cannot be repaired by the board API.

Failures leave request status and existing outputs intact. If image generation succeeded, preserve the official output and resume saving, QA or candidate registration with the same manifest. If screenshot backfill failed after candidate registration, retry complete with that candidate and extraction. Failed diagnostics do not create a replacement request. Report failures to contact the board separately from the original execution error. Existing legacy execution records remain usable through this entry without changing their frozen input fingerprint.
