# Sequential Page Board

## Preferred execution for an existing request

Use [Single-Page Execution](single-page-execution.md): `page-execution.mjs prepare/start/record/check/finalize/complete` provides a single-page input package, verified guide/prompt cache, frozen per-attempt input records and deterministic saving/registration. The official image tool and evidence-based QA still run for every candidate. The legacy API sequence below remains available for services that have not loaded the new endpoint. Do not treat a missing new endpoint as permission to change boards, recreate requests, or skip freshness checks.

## Independent Visual V2

When the user chooses the visual V2 interface, run `node scripts/create-visual-v2-board.mjs <existing-sequential-board-directory>` to create its sibling `decision_board_visual_v2/`. Existing V2 directories are never overwritten. The clone keeps independent source Markdown, uploads, draft, decisions and task records; existing generated images remain available from the project. Start the V2 service with `node scripts/v4-sequential-review-server.mjs <visual-v2-board-directory> <unused-port>`. Use its URL and request IDs for subsequent generation; do not send results to the original board. Interface rules are in [decision-board-visual-v2/DESIGN_SPEC.md](decision-board-visual-v2/DESIGN_SPEC.md). Both board versions retain the same generation and adoption workflow.

## Page Workflow

Use only when the user wants to choose any page, generate one image, review it in the board, and then continue. Create a separate full copy of the existing V4.1 decision board with `node scripts/create-sequential-review-board.mjs <project-path>`, then start it with `node scripts/sequential-board-control.mjs start <project-path>`. The original `decision_board/` files and standard batch workflow remain intact. The new board is `decision_board_sequential/` and retains the original global settings, page choices, real-image uploads, source editor, save action, and generated-image browser. Its editable decision-version Markdown is copied into the new board so editing there does not alter the original board's source. Do not regenerate or overwrite an existing sequential board; it contains decisions and image acceptance records.

The generation and review controls are integrated into the existing generated-image browser, above its preview; the original version history and image browsing remain available. The user may choose any page. Clicking its generation button confirms the current page choices into the new board's `style_decision.json` and writes a request in `decision_board_sequential/page-flow-requests/<request-id>.json`. Up to two distinct-page requests may be queued, running, or awaiting confirmation at once; never allow two active requests for the same page. The board does not call `image_gen.imagegen` and cannot wake an idle Codex conversation. A browser page has no supported way to send a message to or activate a Codex conversation; do not promise automatic session switching or generation from the board. Provide a copyable session instruction for each queued request, including its request ID. Each session must poll by that ID (`/api/page-flow/requests/next?requestId=<id>`) so it cannot pick up another session's task. When a conversation is active, Codex can process its assigned request; when it is idle, the user must resume it. Keep page guides isolated as `page_guides/slide_XX.md` and prompts as `prompts/slide_XX.md` to avoid concurrent writes. The first accepted page is a formal page and counts toward completion.

Keep a generation action visible in every page state. When generation cannot proceed, present it in a muted, accessible disabled state that still responds to a click with the exact next step and board location. Use state-specific labels for queued, running, candidate review, retry, and adopted pages. Saving a page's Markdown must update that page's `board-data.json` raw content and inline board data; otherwise the source-match guard will incorrectly block generation after a successful save. An unsaved edit on another page must not block the active page.

After saving or refreshing a page's raw Markdown, compare its substantive content headings with `information_groups`: prefer direct subheadings under `页面内容`, then include content headings outside that container and an explicit unheaded-content group for a lone body or table. Exclude titles and source-provided production notes. Offer an explicit sync: keep weights for exact heading matches, archive removed/renamed groups with their prior weights, and add new groups as `unassigned`. Do not generate until the user assigns each new group. Text added beneath an unchanged heading remains in that group.

Codex reads `GET /api/page-flow/requests/next` or the request file, verifies the source and decision hashes, then sends `POST /api/page-flow/run/start` with `{ "requestId": "..." }`. Build or refresh this page's guide and prompt when needed. Apply each `raw_visual_marks` annotation to its exact source span: `replace` means express the meaning as a graphic and do not render the selected words; `soften` means retain every word at lower visual prominence and pair it with a graphic; `text-only` means retain the exact original bullet wording and order without added summary text or a dedicated graphic. Unmarked bullet points default to complete original wording at lower prominence plus a related graphic, which may serve a group. If a mark has `needsReview`, stop and ask the user to re-mark it before generation. Never invent an official logo; use a user-provided or confirmed logo asset, otherwise use a generic pictogram. Generate one body image with the official conversational image tool, run focused QA, finalize the title according to the confirmed mode, and save unique version names such as `body_image/slide_05_v003.png` and `final_image/slide_05_v003.png`. Preserve older files. Send `POST /api/page-flow/run/complete` with `{ "requestId": "...", "body": "body_image/slide_05_v003.png", "final": "final_image/slide_05_v003.png", "qa": "...", "guideHash": "...", "promptHash": "..." }`. On failure, send `POST /api/page-flow/run/fail` with the request ID and a short error. These run endpoints are local only and accept Codex's local request without a browser Origin header. Do not claim generation started until the start receipt succeeds.

### Input freshness and real-image integrity (mandatory)

Treat the current confirmed board state as the sole authority for a page-flow task. A request ID identifies the task; it does not prove that its captured content is still current. Before starting and again immediately before image generation, fetch that exact request by ID and freshly read the active decision-version page body, current page and global decisions, active user notes, and the actual uploaded files from the board directory. Use the active `### 页面内容` (or explicitly designated body section), excluding hidden legacy annotation sections. Confirm the body matches the board's saved page content and that the request refers to the same page, board root, and current decisions. Never substitute the preserved original outline, another board version, another request, an old prompt, guide, or conversation memory for the active board.

Build an explicit per-request input manifest before generation: active body text/revision; normalized page and global decisions; each included real image's current board-relative and resolved path, user-selected role/link, and SHA-256 of its bytes; and any palette-reference asset separately marked `colors-only`. Only files listed in the current decision's active image slots/links may be passed as real-image inputs. Removed uploads may remain on disk as historical files; their existence does not authorize reuse. Read and inspect every active image, and check prompt/guide image references against the manifest. A path alone is insufficient: if bytes at that path changed, treat the input as changed. Do not resurrect a deleted image, old label, lock, or prompt instruction from prior requests or generated artifacts.

Use one consistent input revision/fingerprint for the body, decisions, and asset manifest; compare like-for-like fields only. Do not compare an API semantic decision hash with a whole-file JSON hash, or infer that a user edited after submission from hashes with different scopes. Recheck the same inputs before `run/start`, before generation, at `run/complete`, and before adoption/current-status claims. If any active input changed, stop that run as stale; preserve its image only as historical and rebuild the page guide and prompt from the latest confirmed inputs before a new request. Never clear a pending-rebuild marker or claim an artifact current based only on caller-supplied nonempty hashes: verify the actual guide and prompt files and their contents against the current manifest.

For legacy requests that store hashes and paths rather than full snapshots, missing snapshot fields alone are not a generation blocker. Fetch the exact request and the current page from `/api/page-flow/snapshot`; verify `sourceMatches`, `reviewedForGeneration`, and matching source and decision hashes using identical hash scopes. Freshly read the active source and confirmed decisions, resolve only their active assets, and freeze the body text, decision snapshot, and asset byte hashes in a request-local execution manifest before generation. This captures the inputs at execution time; do not claim it proves the asset bytes at original submission time. Recheck these frozen inputs before the tool call and completion. Do not ask the user to repeat a generation command merely because a legacy request lacks snapshots or an endpoint lacks automatic enforcement when the agent can perform the equivalent checks. Stop only for an actual revision mismatch, source/board disagreement, missing or unreadable required assets, unresolved review, or inability to verify the current inputs. Repeating a chat instruction with the same request ID does not create or refresh a board request. Use live API state for task status; creation-time request JSON files may retain an old status. Keep the task scoped to its supplied request ID and page. A candidate remains unadopted until the user explicitly accepts it; never process the next page automatically.

For every generation attempt, save the exact tool prompt and input-path list before calling the image tool, then use those saved values without rewriting them inline. Hash the exact saved UTF-8 prompt actually sent to the tool. Give repair attempts distinct prompt records and bind the candidate to the successful attempt, not an earlier or approximately equivalent prompt. Record the tool output path/output hint and active asset byte hashes. If the saved prompt differs from the tool-call prompt, disclose the provenance mismatch; never certify its hash as the actual generation input. Resolve guide/prompt paths through the request-local manifest rather than silently falling back to an older canonical page file.

The completion QA field must report content compliance and visual completion separately, each with observable evidence. Correct text, valid dimensions, and repaired cell spans do not establish visual completion. If a visual gate fails or was not checked, report fail/unresolved and follow the repair or limitation path; reaching an automatic-retry limit never turns a failed image into a passing candidate.

When diagnosing a mismatch, report evidence separately: active source path/body revision, current decision revision, active image count/names and byte hashes, request ID/state and captured inputs, guide/prompt revision, and candidate lineage. Historical files and cancelled/stale requests should be labelled as such. A successful source save does not prove that generation consumed the new body or images; verify the request and prompt inputs themselves.

The user adopts, rejects, or requests a redo in the new panel. Adoption records the exact final image file and source and decision hashes, then selects the next unfinished page while still allowing free navigation. “取消采用” returns a still-current adopted image to candidate status; if its source or decisions changed, it becomes stale and must be generated again before acceptance. A source or decision change marks an adopted page for review but preserves its old image and record. Existing images of unknown lineage remain visible in the original browser as historical versions and are not automatically adopted.

After all intended pages have adopted versions, check page completeness, source and decision validity, title safety, visual consistency, and final image dimensions. Reopen only pages with an actual issue. The standard `final_image/slide_XX.png` delivery aliases may be produced from accepted version files during final delivery, preserving prior files before any replacement.
