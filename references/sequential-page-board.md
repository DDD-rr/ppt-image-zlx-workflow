# Sequential Page Board

Use only when the user wants to choose any page, generate one image, review it in the board, and then continue. Create a separate full copy of the existing V4.1 decision board with `node scripts/create-sequential-review-board.mjs <project-path>`, then start it with `node scripts/sequential-board-control.mjs start <project-path>`. The original `decision_board/` files and standard batch workflow remain intact. The new board is `decision_board_sequential/` and retains the original global settings, page choices, real-image uploads, source editor, save action, and generated-image browser. Its editable decision-version Markdown is copied into the new board so editing there does not alter the original board's source. Do not regenerate or overwrite an existing sequential board; it contains decisions and image acceptance records.

The generation and review controls are integrated into the existing generated-image browser, above its preview; the original version history and image browsing remain available. The user may choose any page. Clicking its generation button confirms the current page choices into the new board's `style_decision.json` and writes a request in `decision_board_sequential/page-flow-requests/<request-id>.json`. Up to two distinct-page requests may be queued, running, or awaiting confirmation at once; never allow two active requests for the same page. The board does not call `image_gen.imagegen` and cannot wake an idle Codex conversation. A browser page has no supported way to send a message to or activate a Codex conversation; do not promise automatic session switching or generation from the board. Provide a copyable session instruction for each queued request, including its request ID. Each session must poll by that ID (`/api/page-flow/requests/next?requestId=<id>`) so it cannot pick up another session's task. When a conversation is active, Codex can process its assigned request; when it is idle, the user must resume it. Keep page guides isolated as `page_guides/slide_XX.md` and prompts as `prompts/slide_XX.md` to avoid concurrent writes. The first accepted page is a formal page and counts toward completion.

Keep a generation action visible in every page state. When generation cannot proceed, present it in a muted, accessible disabled state that still responds to a click with the exact next step and board location. Use state-specific labels for queued, running, candidate review, retry, and adopted pages. Saving a page's Markdown must update that page's `board-data.json` raw content and inline board data; otherwise the source-match guard will incorrectly block generation after a successful save. An unsaved edit on another page must not block the active page.

After saving or refreshing a page's raw Markdown, compare the direct subheadings under `页面内容` with that page's `information_groups`. Offer an explicit sync: keep weights for exact heading matches, archive removed/renamed groups with their prior weights, and add new headings as `unassigned`. Do not generate until the user assigns each new group. Text added beneath an unchanged heading remains in that group.

Codex reads `GET /api/page-flow/requests/next` or the request file, verifies the source and decision hashes, then sends `POST /api/page-flow/run/start` with `{ "requestId": "..." }`. Build or refresh this page's guide and prompt when needed. Apply each `raw_visual_marks` annotation to its exact source span: `replace` means express the meaning as a graphic and do not render the selected words; `soften` means retain the words at lower visual prominence and pair them with a graphic. If a mark has `needsReview`, stop and ask the user to re-mark it before generation. Never invent an official logo; use a user-provided or confirmed logo asset, otherwise use a generic pictogram. Generate one body image with the official conversational image tool, run focused QA, finalize the title according to the confirmed mode, and save unique version names such as `body_image/slide_05_v003.png` and `final_image/slide_05_v003.png`. Preserve older files. Send `POST /api/page-flow/run/complete` with `{ "requestId": "...", "body": "body_image/slide_05_v003.png", "final": "final_image/slide_05_v003.png", "qa": "...", "guideHash": "...", "promptHash": "..." }`. On failure, send `POST /api/page-flow/run/fail` with the request ID and a short error. These run endpoints are local only and accept Codex's local request without a browser Origin header. Do not claim generation started until the start receipt succeeds.

The user adopts, rejects, or requests a redo in the new panel. Adoption records the exact final image file and source and decision hashes, then selects the next unfinished page while still allowing free navigation. “取消采用” returns a still-current adopted image to candidate status; if its source or decisions changed, it becomes stale and must be generated again before acceptance. A source or decision change marks an adopted page for review but preserves its old image and record. Existing images of unknown lineage remain visible in the original browser as historical versions and are not automatically adopted.

After all intended pages have adopted versions, check page completeness, source and decision validity, title safety, visual consistency, and final image dimensions. Reopen only pages with an actual issue. The standard `final_image/slide_XX.png` delivery aliases may be produced from accepted version files during final delivery, preserving prior files before any replacement.
